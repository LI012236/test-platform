# 接口自动化测试平台 · 设计文档

> 定位：把现有的 pytest 命令行框架，升级成「能在网页上配接口、编用例、跑执行、看报告」的平台。
> 被测对象直接用 `order-mall`，形成「我写服务 → 我写平台测它」的闭环。

## 一、目标与非目标

### 做

| 模块 | 内容 |
|---|---|
| 用户 | 注册 / 登录 / token 鉴权 |
| 项目 | 一个项目对应一套被测系统 |
| 环境 | dev / test / prod，各自 base_url + 公共 Header |
| 接口 | 维护接口定义：方法、路径、Header、Body |
| 用例 | 多个接口串成一条用例，支持变量提取与断言 |
| 执行 | 一键执行、异步跑、并发执行多条用例 |
| 报告 | 运行记录、通过率、单步请求/响应快照、失败原因 |

### 不做（第一版）

- UI 自动化（Selenium）
- 性能压测（JMeter）
- 复杂 RBAC（只有项目成员与管理员）
- 定时任务、CI 接入（列入第二版）

## 二、技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Spring Boot 3.2.5 + JDK 17 + JdbcTemplate + MySQL 8 | 与 order-mall 同栈，代码风格可复用 |
| HTTP 客户端 | JDK `java.net.http.HttpClient` | 不引第三方依赖，超时/重试自己控 |
| 并发 | `ThreadPoolExecutor` | 用例级并发，步骤内串行 |
| 前端 | Vue 3 + Vite + Element Plus | 复用 order-mall 的工程结构 |
| 鉴权 | 内存 Token + 拦截器 | 与 order-mall 一致 |

## 三、数据模型（8 张表）

```
sys_user     id, username, password, salt, nickname, role, created_at
project      id, name, description, owner_id, created_at
env          id, project_id, name, base_url, headers_json, created_at
api          id, project_id, name, method, path, headers_json, body, created_at
test_case    id, project_id, name, description, created_at
test_step    id, case_id, sort, api_id, override_headers, override_body,
             extractors_json, assertions_json, created_at
run          id, project_id, case_id, env_id, status, total, passed, failed,
             duration_ms, started_at, finished_at, error_msg
run_detail   id, run_id, step_id, sort, status, request_snapshot, response_snapshot,
             assertions_result, duration_ms, error_msg
```

**设计要点**

| 字段 | 为什么 |
|---|---|
| `run_detail.request_snapshot` | 存实际发出的请求（含变量替换后的真实值），失败时能复现 |
| `run_detail.response_snapshot` | 存响应体（截断 4KB），报告里可直接看 |
| `test_step.sort` | 步骤有顺序，前一步提取的变量给后一步用 |
| `extractors_json` | 变量提取规则，如 `{"token": "$.data.token"}` |
| `assertions_json` | 断言规则，如 `[{"type":"status","expect":200}]` |

## 四、执行引擎（核心，也是面试重点）

```
输入：case_id + env_id
  ↓
1. 加载用例步骤（按 sort 排序）
2. 初始化变量池：环境变量（base_url、公共 header）
3. 逐步执行：
   a. 渲染请求：把 ${var} 替换成变量池里的值
   b. 发 HTTP 请求（连接超时 3s / 读超时 10s）
   c. 记录请求与响应快照
   d. 执行变量提取器（JSONPath），写回变量池
   e. 执行断言（状态码 / JSONPath / 响应时间 / 包含文本）
   f. 有断言失败 → 标记该步骤失败（默认中断后续步骤，可配置继续）
4. 汇总：total / passed / failed / duration
5. 落库：run + run_detail
```

**五个关键决策（面试可讲）**

1. **为什么自研引擎不用 pytest**：平台要支持「用户在网页上配的用例」，本质是数据驱动；pytest 适合写死的代码用例。自研引擎执行的是 JSON 配置，与语言无关。
2. **变量作用域**：环境变量 → 用例变量 → 提取变量，后覆盖前；步骤间靠变量池传递。
3. **断言失败策略**：默认中断（快速失败），可配置 `continue_on_fail` 跑完全部步骤拿到完整报告。
4. **并发模型**：用例级并行（线程池），单条用例内步骤串行（有依赖）。同一用例并发跑没有意义，会互相覆盖变量。
5. **失败可定位**：每个步骤都存请求/响应快照，报告里点开就能看到「发了什么、回了什么、哪条断言挂了」。

## 五、接口清单（24 个）

| 模块 | 接口 |
|---|---|
| 认证 | `POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me` |
| 项目 | `GET/POST /api/projects`、`PUT/DELETE /api/projects/{id}` |
| 环境 | `GET/POST /api/projects/{pid}/envs`、`PUT/DELETE /api/envs/{id}` |
| 接口 | `GET/POST /api/projects/{pid}/apis`、`PUT/DELETE /api/apis/{id}` |
| 用例 | `GET/POST /api/projects/{pid}/cases`、`PUT/DELETE /api/cases/{id}` |
| 步骤 | `GET/POST /api/cases/{cid}/steps`、`PUT/DELETE /api/steps/{id}` |
| 执行 | `POST /api/cases/{cid}/run`（异步）、`GET /api/runs/{id}`（轮询状态） |
| 报告 | `GET /api/projects/{pid}/runs`、`GET /api/runs/{id}/details` |

## 六、前端页面（6 个）

| 路由 | 页面 | 内容 |
|---|---|---|
| `/login` | 登录 / 注册 | 同 order-mall |
| `/projects` | 项目列表 | 卡片 + 新建 |
| `/projects/:id/apis` | 接口管理 | 表格 + 弹窗编辑（方法/路径/头/Body） |
| `/projects/:id/cases` | 用例列表 | 表格 + 新建 + 进入编辑 |
| `/cases/:id` | 用例编辑 | 步骤列表（上移/下移）、每步配断言与提取、右侧调试 |
| `/runs/:id` | 执行报告 | 通过率、步骤时间线、请求/响应快照、失败原因 |

## 七、四周排期

| 周 | 内容 | 产出 |
|---|---|---|
| W1 | 骨架 + 用户/项目/环境 + 接口 CRUD | 能登录、能建项目、能维护接口 |
| W2 | 用例与步骤 CRUD + 执行引擎（同步版） | 命令行调接口能跑通用例 |
| W3 | 异步执行 + 报告落库 + 前端 3 页（登录/项目/接口） | 网页能发起执行并看结果 |
| W4 | 用例编辑页 + 报告页 + 种子数据（导入 order-mall 的 24 个接口） | 完整闭环 + 演示 |

## 八、验收标准

- [ ] 网页上能新建项目、环境、接口、用例
- [ ] 用例支持多步骤串联，前一步提取的 token 能给后一步用
- [ ] 一键执行，3 秒内返回 run_id，报告页自动刷新出结果
- [ ] 断言失败能定位到具体步骤、具体断言、实际值
- [ ] 内置 order-mall 的种子接口，登录后能直接跑通「登录 → 查商品 → 加购 → 下单」用例
- [ ] README + 接口文档 + 一张架构图

## 九、和已有资产的关系

| 已有 | 复用方式 |
|---|---|
| `order-test-project`（pytest 框架） | 思路复用：分层、数据驱动、断言设计；平台是它的 Web 版 |
| `order-mall` | 作为被测系统，导入其 24 个接口作为种子数据 |
| order-mall 的骨架 | 直接复制后端分层与鉴权、前端工程结构 |
